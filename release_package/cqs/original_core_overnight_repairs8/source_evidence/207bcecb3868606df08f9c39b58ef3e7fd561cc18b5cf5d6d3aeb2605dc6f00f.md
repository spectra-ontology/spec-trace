    ### 1.1 What is the domain?
    
    **3GPP RAN3 Final Report 본문에 기록된 Resolution(결의) 정보 및 역할 정보**
    
    > **용어 사전 (Final Report 표기 통일)**: 3GPP 공식 문서 제목은 "**Final Minutes Report**"이지만, 본 프로젝트 전반(Phase-1~2, Phase-6~9 포함)에서는 약칭으로 "**Final Report**"를 사용한다. Phase-6 §2.5.1의 "Final Minutes Report" 표기 및 외부 3GPP 문서 인용 문맥에서는 공식 명칭이 그대로 등장할 수 있으나, 본 Spec의 모든 설명·CQ·속성 정의는 "Final Report"로 통일되어 있다. 양자는 동일 문서를 지칭한다.
    
    RAN3 Final Report는 **Resolution 텍스트 블록**(`Agreement:`, `Conclusion:`, `Working Assumption:`/`WA:`)과 **Decision 패턴**(`Decision: The document was agreed.`)이 공존하는 구조를 가진다.
    
    > **용어 사전 (Working Assumption 표기 통일)**: 본 Spec 전반에서 세 표기는 동일 개념의 서로 다른 레이어를 지칭하는 것으로 고정한다.
    > - `WorkingAssumption` — **OWL 클래스명** (코드·TTL·JSON-LD `@type`)
    > - `Working Assumption` — **자연어/개념 명칭** (본문 설명용)
    > - `WA` — **원문 축약 패턴** (Final Report 본문에 `WA:` 헤더로 등장). 파서 정규식 매칭 대상
    > 
    > Step 3 §3.1과 Step 7 §6.2의 "`Working Assumption:` 및 `WA:` 통합"은 원문 패턴 두 가지(`Working Assumption:`, `WA:`) 모두 같은 `WorkingAssumption` 인스턴스로 적재한다는 의미이며, 세 표기는 이 규칙에 따라 일관되게 사용된다.
    
    - Resolution: 기술적 합의 내용 원문 (Agreement + Conclusion + WA. 실측치는 Appendix A [P2-V01], [P2-V02], [P2-V03], [P2-V08] 참조)
    - Decision: 문서 단위 처리 결과 — Phase-1 status와 중복이므로 Phase-2 Scope 밖
    - Moderator: 논의 진행자 역할 (구조화. 실측치는 Appendix A [P2-V05] 참조)

    ### 1.7 RAN3 Phase-2 Resolution과 Decision의 관계 (권위 정의)
    
    > 본 §1.7이 Phase-2 Spec 내 Resolution vs Decision 구분의 **권위 정의**이다. Step 3 §3.2 "제외 대상" 표, Step 5 §6.3 "RAN3 클래스 포함/제외 결정" 등 이후 나오는 유사 서술은 본 절을 반복 근거로 하며, 상세 설명은 §1.7를 참조한다.
    
    RAN3 Final Report에서 **Resolution과 Decision은 서로 다른 레벨의 정보**이다:
    
    ```
    [TDoc] R3-242126 CB:#6_LTM (discussion)
      Decision: The document was noted.     ← TDoc 단위 처리 결과 (Phase-1 status)
      Agreement: TA validity assurance...   ← 기술적 합의 내용 (Resolution 원문)
      Agreement: gNB-CU assigns the...      ← 기술적 합의 내용 (Resolution 원문)
      WA: gNB-CU indicates the IDs...       ← 잠정 합의 (Resolution 원문)
    ```
    
    - **하나의 TDoc 논의에서 여러 Resolution이 도출**될 수 있음
    - Decision이 `noted`여도 그 안에서 기술적 Agreement가 도출됨
    - Phase-2는 **Resolution 텍스트 블록만 추출** (Decision은 Phase-1 status로 커버)

    ## 3. Scope 정의
    
    ### 3.1 포함 (In Scope)
    
    | 구분 | 포함 대상 | 비고 |
    | --- | --- | --- |
    | **Resolution** | Agreement, Conclusion, Working Assumption | CQ1~3, CQ6 |
    | **역할** | Summary (Moderator 기반) | CQ4, CQ6-3. **RAN3에서 포함** |
    | **Embedded Content** | Table | Resolution 완결성 위해 포함 |
    | **데이터 소스** | Final Report 본문 | Annex 제외 |
    
    ### 3.2 제외 (Out of Scope)
    
    | 제외 대상 | 이유 |
    | --- | --- |
    | `Decision:` 패턴 | Phase-1 status와 중복. Resolution이 아닌 문서 처리 결과 |
    | SessionNotes (Chair) | 구조화 패턴 없음. Chair 언급은 있으나 SessionNotes 형태 아님 |
    | Rapporteur | 본문 키워드로 다수 등장하나 구조화 어려움 (역할-회사 매핑 불가) |
    | Annex (B, C, D, E, F) | 본문만 파싱 원칙 |
    | Figure/Chart/Equation | Figure 극소수, Chart 0건, 수식 0건 |
    | contentWithEquations | 수식 0건 |
    | CQ5 (후속 조치) | Annex 의존 |

    ## Step 5: 속성(Slot) 정의
    
    > Ontology 101 원칙
    >
    >
    > *"Define the properties of classes—slots... Properties describe attributes of instances of a class and relations to other instances."*
    >
    > — Noy & McGuinness, Ontology Development 101
    >
    
    ---
    
    ## 1. Step 5 목적
    
    - Step 4에서 정의한 클래스의 **속성(Slot)** 정의
    - **Data Property**: 클래스 인스턴스의 값 (String, Integer, Boolean 등)
    - **Object Property**: 클래스 인스턴스 간의 관계
    - 제약조건(Cardinality 등)은 Step 6에서 정의
    
    ---
    
    ## 2. 속성의 종류
    
    | 종류 | 설명 | 예시 |
    | --- | --- | --- |
    | **Data Property** | 객체의 속성값 | content, hasFFS |
    | **Object Property** | 다른 객체와의 관계 | references, madeAt |

    ## 3. Resolution 계층 속성
    
    ### 3.1 Resolution (추상 클래스)
    
    하위 클래스(Agreement, Conclusion, WorkingAssumption)가 **공통으로 상속**하는 속성
    
    **Data Property**
    
    | Property | Type | Description |
    | --- | --- | --- |
    | resolutionId | String | Resolution 고유 식별자 (예: AGR-124-8.1-001) |
    | content | String | Resolution 본문 텍스트 |
    | sequence | Integer | 같은 Agenda 내 순서 |
    | sessionContext | String | 세션 정보 (예: "Thursday session", "Online") |
    | note | String | 부가 설명 (Note: ...) |
    
    > `contentWithEquations` 미정의: RAN3 수식 0건이므로 content만 사용 (Step 1 §1.6 근거)
    
    **Object Property**
    
    | Property | Range | Description |
    | --- | --- | --- |
    | references | Tdoc | Resolution이 참조하는 Tdoc |
    | madeAt | Meeting | Resolution이 도출된 회의. Phase-1 Meeting의 `canonicalMeetingNumber`와 매칭 |
    | resolutionBelongsTo | AgendaItem | Resolution이 속한 Agenda |
    | hasTable | Table | Resolution이 참조하는 Table |
    
    > `hasFigure`/`hasChart` 미정의 (RAN3은 Figure/Chart 클래스 없음)

    > **🔴 Phase-1 ↔ Phase-2 정규화 일관성 (필수)**: Phase-2 loader는 `madeAt`/`containedIn`에서 추출한 canonical을 **Phase-1과 동일한 정규화 함수**로 처리한 후 `MERGE` 키로 사용해야 한다. Phase-1은 canonical에서 `-e` suffix 제거 (Phase-1 reference classes 모듈 정규화 함수). Phase-2가 정규화를 생략하면 같은 미팅이 두 노드로 분기되어 NULL id placeholder 발생. `MERGE`의 `ON CREATE SET` 에 `m.id` 속성도 명시 부여 (Phase-1 id 패턴과 동일). 구현: Phase-2 loader의 canonical 정규화 헬퍼 함수 사용.

    ## Step 6: 제약조건(Facet) 정의
    
    > Ontology 101 원칙
    >
    >
    > *"Define the facets of the slots... Slots can have different facets describing the value type, allowed values, the number of the values (cardinality), and other features of the values the slot can take."*
    >
    > — Noy & McGuinness, Ontology Development 101
    >
    
    ---
    
    ## 1. Step 6 목적
    
    - Step 5에서 정의한 속성의 **제약조건(Facet)** 정의
    - **Cardinality**: 속성값 개수 (0..1, 1, 0..*, 1..*)
    - **필수 여부**: 인스턴스 생성 시 반드시 값이 필요한지
    - **Functional**: 단일값만 허용하는지
    - **Inverse**: 역관계가 있는지
    
    ---
    
    ## 2. Facet 종류
    
    | Facet | 설명 | 예시 |
    | --- | --- | --- |
    | **Cardinality** | 속성값 개수 | 0..1, 1, 0..*, 1..* |
    | **Required** | 필수 여부 | ✅ / ❌ |
    | **Functional** | 단일값만 허용 | ✅ (최대 1개) |
    | **Inverse** | 역관계 | resolutionBelongsTo ↔ hasResolutions |
    
    ### Cardinality 표기법
    
    | 표기 | 의미 | Required | Functional |
    | --- | --- | --- | --- |
    | 1 | 정확히 1개 | ✅ | ✅ |
    | 0..1 | 0개 또는 1개 | ❌ | ✅ |
    | 1..* | 1개 이상 | ✅ | ❌ |
    | 0..* | 0개 이상 | ❌ | ❌ |

    ## 3. ID 생성 규칙
    
    ### 3.1 ID 생성 원칙
    
    | 원칙 | 설명 |
    | --- | --- |
    | 유일성 | 클래스 내에서 고유한 값 |
    | 불변성 | 한 번 생성되면 변경 불가 |
    | 의미성 | 도메인 의미 반영 |
    | 추적성 | 데이터 소스와 매핑 가능 |
    
    ### 3.2 Resolution 계층 ID
    
    | 클래스 | ID 속성 | 패턴 | 예시 |
    | --- | --- | --- | --- |
    | Agreement | resolutionId | `AGR-{meeting}-{agenda}-{seq}` | AGR-124-8.1-001 |
    | Conclusion | resolutionId | `CON-{meeting}-{agenda}-{seq}` | CON-124-9.2-001 |
    | WorkingAssumption | resolutionId | `WA-{meeting}-{agenda}-{seq}` | WA-124-8.1-001 |
    
    **ID 구성 요소**:
    
    - `{meeting}`: 회의 번호 (resolutionId 토큰 **원본 표기** 예: 91, 100, 124, 121-bis). `madeAt → Meeting.canonicalMeetingNumber`는 Phase-1 §6.1 규칙(`-bis → bis`)에 따라 `RAN3#121bis`로 저장한다.
    - `{agenda}`: Agenda Item 번호 (예: 8.1, 9.2.1)
    - `{seq}`: 해당 Agenda 내 순번 (001, 002, ...)
    
    > bis 3변종 포함 (예: AGR-121-bis-8.1-001, AGR-114bis-e-8.1-001). 대소문자 무시 처리. resolutionId 내 `121-bis`·`114bis-e` 토큰은 파일명 원본을 보존한 형식이며, Meeting 매칭에는 canonical 규칙을 적용한다.
    
    ### 3.3 Summary ID
    
    | 클래스 | ID 속성 | 패턴 | 예시 |
    | --- | --- | --- | --- |
    | Summary | (Tdoc 상속) | `SUM-{meeting}-{agenda}-{seq}` | SUM-124-8.1-001 |
    
    > Summary ID는 Resolution ID 패턴과 동일 구조를 따름.
    
    ### 3.4 Embedded Content ID
    
    | 클래스 | ID 속성 | 패턴 | 예시 |
    | --- | --- | --- | --- |
    | Table | tableId | `TBL-{meeting}-{seq}` | TBL-124-001 |
    
    **ID 구성 요소**:
    
    - `{meeting}`: 회의 번호 (예: 91, 100, 124, 121-bis)
    - `{seq}`: 해당 회의 내 순번 (001, 002, ...)

    ## 4. 데이터 소스 매핑
    
    ### 4.1 Resolution 매핑
    
    **소스**: Final Report 본문
    
    | 관계 | 소스 | 변환 규칙 |
    | --- | --- | --- |
    | references → Tdoc | content 내 참조 | `R3-\\d{6}` 패턴 추출 (6자리) |
    | madeAt → Meeting | 문서 메타 | 파일명에서 회의 번호 추출 후 Phase-1 Meeting의 `canonicalMeetingNumber`와 매칭 |
    | resolutionBelongsTo → AgendaItem | 섹션 헤더 | Agenda 번호 추출. **같은 미팅 내의 AgendaItem과 매칭** (madeAt으로 결정된 Meeting의 AgendaItem) |
    | hasTable → Table | 결정 본문 블록 범위 | 결정의 `body_blocks`(표지 줄 블록부터 본문 끝 문단 블록 앞까지의 `[시작, 끝)`) 안에 `paragraph_index` 가 놓인 같은 미팅 TBL 인스턴스 연결 |
    
    *참고: hasTable 은 결정 글에 적힌 `Table N` 번호로 잇지 않는다(RAN1 과 같은 규칙). 결정 글의 번호는 대개 TS 나 다른 Tdoc 의 표를 가리키기 때문이다. 세부는 Step 1 의 「주의」에 있다.*
    
    > TDoc 패턴: `R3-\\d{6}` (**RAN3은 6자리**)
    
    **references → Tdoc 매칭 실패 시 처리 규칙:**
    
    | 조건 | 처리 |
    | --- | --- |
    | 추출된 Tdoc 번호가 Phase-1 인스턴스에 존재 | 기존 인스턴스에 references 관계 생성 |
    | 추출된 Tdoc 번호가 Phase-1 인스턴스에 없음 | references 관계 생성 안 함 + 로그 기록 |
    
    *참고: Resolution 본문에서 추출된 `R3-\\d{6}` 패턴이 Phase-1 Tdoc 인스턴스에 존재하지 않을 수 있음. 이 경우 동적 생성하지 않고 관계를 생략함*
    
    **Meeting 연결 규칙:**
    
    | Final Report 파일명 | 추출된 회의 번호 | 매칭 대상 (Phase-1) |

    | Final_Report_RAN3-124.docx | RAN3#124 | canonicalMeetingNumber = "RAN3#124" |
    | Final_Report_RAN3-121-bis.docx | RAN3#121bis (Phase-1 §6.1 정규화: `-bis` → `bis`) | canonicalMeetingNumber = "RAN3#121bis" (Neo4j 실측 일치) |
    | Final_Report_RAN3-119bis.docx | RAN3#119bis | canonicalMeetingNumber = "RAN3#119bis" |
    
    **미팅 번호 추출:**
    
    > 파일명 기반으로 미팅 번호 추출. bis 3변종(bis/Bis, bis-e, -bis) 대소문자 무시 처리.

    ### 4.6 Table 매핑
    
    **소스**: Final Report 본문 `<w:tbl>`
    
    **식별 기준**:
    
    1. 캡션 기반: 표 바로 앞 세 문단 안에 `Table {번호}` 제목 문단(`caption.TABLE`)이 있는 경우. 번호는 Tdoc 캡션과 같은 단 문법으로 읽어 부록 글자 · 글자 꼬리 · 자리표 · 로마 숫자를 받는다(`7.8-1` · `6.1.1-x` · `A.3-1` · `7.3.1.1.2-5E` · `X.12`). 숫자와 `.` · `-` 만 받는 번호는 RAN1#111 의 `Table 6.1.1-x: BS energy savings …` 를 번호 `6.1.1` 과 제목 `x: …` 로 갈랐다
    2. 구조 기반: 캡션 없는 `<w:tbl>` 중 (행 수 > 3) AND (숫자/수식 포함) AND (agenda/일정표 패턴 제외)
    
    *Note: 단순 포맷팅 테이블 (agenda, 일정표, Tdoc 목록 등)은 제외*
    
    | 속성 | 소스 | 변환 규칙 |
    | --- | --- | --- |
    | tableId | 자동 생성 | `TBL-{meeting}-{seq}` |
    | caption | 본문 패턴 | `Table {번호}: {제목 글}` (제목 글이 없으면 `Table {번호}`) |
    | filePath | 변환 저장 | HTML 파일 경로 |
    | tableNumber | 캡션 패턴 | `Table {번호}` (예: `Table 6.1.1-x` · `Table A.3-1`) |
    
    | 관계 | 소스 | 변환 규칙 |
    | --- | --- | --- |

    ### 4.8 Null 값 처리 규칙
    
    | 속성/관계 | 상황 | 처리 | 로그 레벨 |
    | --- | --- | --- | --- |
    | content | 파싱 실패 | Resolution 인스턴스 미생성 | ERROR |
    | references | Tdoc 번호가 Phase-1 인스턴스에 없음 | 해당 참조만 스킵 (§4.1 참조) | WARNING |
    | references | Tdoc 번호 파싱 실패 | 해당 참조만 스킵 | WARNING |
    | moderatedBy | 회사명 파싱 실패 | null 유지 (정상) | WARNING |
    | caption (Table) | 캡션 없음 | null 유지 (정상) | - |
    
    **처리 원칙:**
    
    - `content`(Resolution)은 필수 속성(Cardinality: 1)이므로 값을 채울 수 없으면 인스턴스 자체를 생성하지 않음
    - `moderatedBy`는 선택 속성(Cardinality: 0..1)이므로 파싱 실패 시 null이 정상
    - `caption`은 선택 속성(Cardinality: 0..1)이므로 null이 정상
