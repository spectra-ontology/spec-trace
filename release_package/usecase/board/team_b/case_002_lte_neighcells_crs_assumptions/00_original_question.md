## Question body (meaning preserved verbatim from the original)

I have a question about the lte-NeighCellsCRS-AssistInfoList-r17 IE in TS38.331, specifically the additionally described lte-NeighCellscRS-Assumptions content. LTE-NeighCellsCRS-AssistInfoList is an IE that provides information on neighbour LTE cells for CRS interference mitigation, and it is specified that if the CRS port number / Channel bandwidth / Centre frequency / MBSFN configuration within this IE are not configured, they can be referenced from the RateMatchPatternLTE-CRS configured for the Serving cell. lte-NeighCellsCRS-Assumptions If the field is not configured, the following default network configuration assumptions are valid for all LTE neighbour cells for the purpose of CRS interference mitigation (CRS-IM) in scenarios with overlapping spectrum for LTE and NR (see TS 38.101-4 [59]). - The CRS port number is the same as the one indicated in RateMatchPatternLTE-CRS if configured for the serving cell. - The CRS port number is 4 if RateMatchPatternLTE-CRS is not configured for the serving cell. - The channel bandwidth and centre frequency are the same as the ones indicated in RateMatchPatternLTE-CRS if configured for the serving cell. - The MBSFN configuration is the same as the one indicated in RateMatchPatternLTE-CRS if configured for the serving cell. If RateMatchPatternLTE-CRS is not configured for the serving cell, MBSFN subframe is not configured. - Network-based CRS interference mitigation (i.e., CRS muting), as in crs-IntfMitigConfig specified in TS 36.331 [10], is not enabled. If the field is configured (i.e. false) and LTE-NeighCellsCRS-AssistInfoList is configured, the configuration provided in LTE-NeighCellsCRS-AssistInfoList overrides the default network configuration assumptions. If the field is configured (i.e. false) and LTE-NeighCellsCRS-AssistInfoList is not configured, it is up to the UE implementation whether to apply CRS-IM operation. Here, the RateMatchPatternLTE-CRS information configured for the Serving cell appears to be delivered via lte-CRS-ToMatchAround (Rel.15) or lte-CRS-PatternList1 (Rel.16) within ServingCellConfig. In the case of Rel.15 lte-CRS-ToMatchAround, a single pattern is delivered, so the application of the above assumptions is clear; however, for lte-CRS-PatternList1 (Rel.16), which is delivered as a list, the application criteria are ambiguous, hence this question. When the configuration is delivered as LTE-CRS-PatternList-r16, could you please confirm whether application of these assumptions is supported, and if so, by what criteria the elements within the list should be mapped in order to reference the freqDL, BandwidthDL, mbsfn configuration, and CRS port number that lte-NeighCellsCRS-AssistInfoList should refer to. LTE-CRS-PatternList-r16 ::= SEQUENCE (SIZE (1..maxLTE-CRS-Patterns-r16)) OF RateMatchPatternLTE-CRS maxLTE-CRS-Patterns-r16 INTEGER ::= 3 -- Maximum number of additional LTE CRS rate matching patterns LTE-NeighCellsCRS-AssistInfoList-r17 ::= SEQUENCE (SIZE (1..maxNrofCRS-IM-InterfCell-r17)) OF LTE-NeighCellsCRS-AssistInfo-r17 maxNrofCRS-IM-InterfCell-r17 INTEGER ::= 8 -- Maximum number of LTE interference cells for CRS-IM per UE Thank you.
